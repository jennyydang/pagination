Example SSR

6 pages, 3 results each. This instance is deliberately not a .c-pagination element, so pagination.js never discovers or touches it — reusing only its nested BEM classes for identical styling. Every page number below is a real <a href="?ssr_page=N">; clicking one does a genuine full browser navigation, and the markup — which page is "current", which results show, which arrow is disabled — is (re)computed from that URL on load by a tiny separate script, the way a real server template would render it per-request. The prev/next arrows are real <button> elements though, so, like the rest of this component, they need JavaScript to do anything — they're inert here on purpose, and there's no mobile "go to page" form for the same reason. (This static file server has no real backend, so the tiny script below is standing in for one — it only fills in a different page's markup when JS actually runs; the page-1 markup you see on first load is plain, pre-rendered HTML with nothing missing.)

Example AJAX

500 results, 10 per page, so 50 pages of c-pagination links control the list below. Both are real, server-renderable markup: page 1's results and page list are hand-authored HTML, not built by JavaScript. Clicking a result link, a page link, an arrow, the mobile input, or an ellipsis jump all fire the same pagination:navigate event, which this page listens for to re-render just the results list (no full page reload) and updates the URL via pushState.
